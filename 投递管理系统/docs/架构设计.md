## 1. 架构总览

### 1.1 容器视图（C4 Level 2）

```
┌──────────────────────────────────────────────────────────────────────┐
│                          秋招投递管理平台                                │
│                                                                        │
│  ┌────────────────┐        HTTPS/JSON         ┌────────────────────┐  │
│  │  Vue 前端        │ ───────────────────────▶ │   FastAPI 后端      │  │
│  │  (frontend/)    │ ◀─────────────────────── │   (backend/app)     │  │
│  │  看板/列表/统计  │       REST /api/v1        │   API→Service→Repo  │  │
│  └────────────────┘                           └─────────┬──────────┘  │
│       │ 文件上传/预览                                │    │           │
│       │                                            │    │           │
│       │                                     ┌──────▼─┐  ┌▼─────────┐ │
│       │                                     │ SQLite │  │  MinIO   │ │
│       │                                     │ 投递/   │  │ 简历/截图 │ │
│       │                                     │ 公司/   │  │ 对象存储  │ │
│       │                                     │ 问题表  │  └──────────┘ │
│       │                                     └────────┘               │
│  ┌────────────────────────────────────────────────────────────────┐ │
│  │  外部操作者：小铜罩（AI 代理）                                    │ │
│  │  通过同一套 REST API 主动录入/更新投递与问题记录（无 UI 也可控）   │ │
│  └────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
```

### 1.2 关键关系

- 前端 ⇢ 后端：单向依赖（前端调后端 API，后端不反向依赖前端）。
- 后端 ⇢ SQLite / MinIO：后端内部依赖，通过 Repository / Storage 抽象隔离。
- 小铜罩代理 ⇢ 后端：与前端**平级**的 API 消费者，复用同一套接口（保证单一数据源）。
- 本地分类目录（`后端开发/测试开发/AI开发/...`）：是**文件归档层**，按总纲中文规范存放简历原件；平台内的 MinIO 是其**可访问副本**。两者由代理同步维护，互不替代。

## 2. 领域模型（边界上下文）

| 上下文 | 职责 | 核心实体 |
| --- | --- | --- |
| 投递上下文 | 管理公司、岗位、投递状态流转 | Company、Application |
| 简历资产上下文 | 管理简历文件版本与存储 | Resume（对象引用） |
| 问题知识上下文 | 记录秋招过程问题并可复盘 | Issue |
| 分析上下文 | 聚合筛选、统计、趋势 | 只读视图，组合上述实体 |

依赖方向：**分析上下文 → 其余三个；问题上下文 → 投递上下文（可选关联）；其余互不依赖。**

## 3. 后端架构（FastAPI）

### 3.1 分层与依赖

```
请求 → API 层(routers) → Service 层(services) → Repository 层(repositories) → Model 层(models)
                                  │                        │
                                  └──→ Storage 层(storage, MinIO)
                                  └──→ Core 层(db/session/config)
```

依赖铁律：**上层依赖下层，下层不反向依赖上层；层内模块按上下文拆分，跨上下文只允许分析层聚合。**

### 3.2 模块职责

| 模块 | 路径 | 职责 |
| --- | --- | --- |
| 入口 | `app/main.py` | 创建 app、挂载路由、CORS、静态/MinIO 代理、生命周期 |
| API 层 | `app/api/*.py` | 路由、参数校验、权限（本期无鉴权）、调用 service |
| Schemas | `app/schemas/*.py` | Pydantic 请求/响应模型（与前端类型对齐） |
| Service 层 | `app/services/*.py` | 业务逻辑（状态流转、关联、统计计算） |
| Repository 层 | `app/repositories/*.py` | 数据访问，封装 SQLAlchemy 查询 |
| Model 层 | `app/models/*.py` | SQLAlchemy ORM 映射 |
| Storage 层 | `app/storage/minio.py` | MinIO 客户端封装、上传/下载/预签名 URL |
| Core | `app/core/` | `config.py`(pydantic-settings)、`db.py`(engine/session)、`deps.py`(依赖注入)、`logging.py` |

### 3.3 目录结构（与现有开发目录对应）

```
backend/
├── app/
│   ├── main.py
│   ├── api/            # applications.py / companies.py / resumes.py / issues.py / analytics.py
│   ├── schemas/        # application.py / company.py / resume.py / issue.py
│   ├── services/       # application_service.py / resume_service.py / issue_service.py / analytics_service.py
│   ├── repositories/   # application_repo.py / company_repo.py / resume_repo.py / issue_repo.py
│   ├── models/         # application.py / company.py / resume.py / issue.py / base.py
│   ├── storage/        # minio.py
│   └── core/           # config.py / db.py / deps.py / logging.py
├── tests/              # pytest，按模块镜像
├── requirements.txt
├── .env.example        # MINIO_ENDPOINT / KEY / SECRET / BUCKET、SQLITE_PATH
└── README.md
```

> 现有 `backend/` 占位目录直接升级为上述结构，无需移动。

## 5. 数据模型（SQLite）

### 5.1 实体关系

```
companies 1──* applications 1──0..1 resumes
issues   0..*──1 applications (related_application_id, 可空)
```

### 5.2 表结构（字段对齐总纲 4.1/4.2）

**companies（公司）**
`id` PK · `name` · `alias` · `city` · `industry` · `website` · `created_at`

**applications（投递记录）**
`id` PK · `company_id` FK · `type`(后端开发/测试开发/AI开发) · `position` · `status`(待投递/已投递/笔试中/面试中/已挂/已Offer/已拒绝/爽约) · `channel`(官网/内推/招聘平台/邮箱) · `apply_date` · `city` · `jd_url` · `resume_id` FK(nullable) · `requirements` · `tailor_notes`(针对性修改说明) · `referrer` · `salary` · `deadline`(nullable) · `notes` · `created_at` · `updated_at`

**resumes（简历资产）**
`id` PK · `company`(快照) · `application_id` FK(nullable) · `filename` · `object_key`(MinIO) · `size` · `content_type` · `is_base`(是否初始简历) · `version` · `uploaded_at`

**issues（问题记录）**
`id` PK · `title` · `category`(面试/笔试/流程/技术/其他) · `related_application_id` FK(nullable) · `description` · `solution` · `tags`(逗号分隔或 JSON) · `recorded_date` · `created_at`

> 枚举值以代码常量集中定义（后端 `core/constants.py`、前端 `utils/enums.ts`），避免散落硬编码。

## 6. MinIO 存储设计

- **Bucket**：单一桶 `qiuzhao`（或按环境分 `qiuzhao-dev`）。
- **Object Key 规则**：`{类型}/{公司名}/{投递批次}/{文件名}`，例：`后端开发/字节跳动/投递1_20260904/柳铜罩_字节跳动_后端.pdf`
- **访问**：后端生成预签名 URL 供前端预览/下载；不直接暴露 MinIO 公网。
- **初始简历**：`is_base=true` 的 resume 记录对应资料库初始简历副本，object_key 置于 `初始简历/` 前缀。

## 7. API 设计约定

- 风格：RESTful，版本前缀 `/api/v1`。
- 统一响应：`{ "code": 0, "message": "...", "data": ... }`（成功 `code=0`，业务/校验错误非零）。
- 状态码：HTTP 状态表达传输层（200/201/400/404/500），业务码表达领域结果。
- 分页：列表接口 `?page=&page_size=`，返回 `{ total, items }`。
- 更新语义：状态/备注变更用 `PATCH /api/v1/applications/{id}`，便于代理增量更新。
- OpenAPI：FastAPI 自动生成 `/docs`，前端类型可由 `openapi.json` 生成（推荐 `openapi-typescript`）。
- 本期无鉴权；若代理与外部共用，后续在 `core/security.py` 加 API Key / Token（不破坏现有接口）。

## 8. 开发规范与编码约定

### 8.1 后端（Python）
- Python ≥ 3.11；FastAPI + SQLAlchemy 2.0 + Pydantic v2。
- 命名：模块/函数 `snake_case`，类 `PascalCase`，常量 `UPPER_SNAKE`。
- DB 会话用依赖注入（`core/deps.py`），禁止全局 session 跨请求。
- 日志用 `core/logging.py` 结构化输出，禁止 `print` 调试。
- 配置走 `pydantic-settings` 读 `.env`，密钥不入库。

### 8.2 前端（Vue + TS）
- Vue 3 `<script setup>` + TypeScript；`camelCase` 变量/函数，`PascalCase` 组件。
- 状态用 Pinia，禁止组件间直接共享裸 ref 跨页。
- API 调用集中在 `src/api/`，页面不直接 `fetch`。
- 枚举/状态文案用 `utils/enums.ts` 统一管理，UI 文案中文。

### 8.3 工程通用
- 提交规范：Conventional Commits（`feat:`/`fix:`/`docs:`/`chore:`），中文描述允许。
- 测试：后端 `pytest`（service/repo 单测），前端 `vitest`（组件/工具）。
- 分支：功能分支 `feature/xxx` → `main`；本仓库单人维护，可简化。

### 8.4 ADR-003 命名约定（重要取舍）

- **背景**：用户偏好「文件夹和文件用中文命名」。
- **决策**：
  - 顶层业务目录、文档、UI 文案：**中文**（如 `投递管理系统`、`投递管理要求.md`、页面标题「投递看板」）。
  - 源码文件与代码标识符：**英文**（`applications.py`、`application.ts`、变量 `applyDate`）。
- **取舍（必须明示）**：中文源码文件名会使 import 路径含非 ASCII、部分构建工具/CI/跨平台文件系统下不稳定，且与 FastAPI/Vue 生态惯例冲突。**为工具链稳定，牺牲源码文件名的中文化**。
- **若坚持全中文源码文件名**：需承担跨平台/工具兼容性风险（git 在部分 OS、esbuild/vite 插件、类型生成可能报错）。
- **状态**：建议（Accepted），由 cuz 最终确认；当前按上述混合方案执行。

## 10. 演进路线

| 阶段 | 目标 | 关键交付 |
| --- | --- | --- |
| **Phase 0** | 脚手架 | 当前 `frontend/`、`backend/` 占位；本文档（已完成） |
| **Phase 1** | 核心 CRUD + 存储 | 公司/投递/简历/问题 增删改查；MinIO 上传预览；Vue 看板/列表/详情/筛选 |
| **Phase 2** | 分析能力 | ECharts 统计仪表盘；按类型/状态/城市/时间多维筛选；deadline 提醒 |
| **Phase 3** | 代理自动化 | 后端 API 完备后，小铜罩使用轻量 HTTP 客户端批量录入/更新；支持「cuz 下令→代理记录」「cuz 报消息→代理更新」闭环 |
| **Phase 4** | 可扩展增强 | 字段插件化（动态扩展属性）；导出 Excel/PDF；多用户/鉴权；本地运行时一键启动脚本 |
| **未来** | 规模升级 | SQLite→PostgreSQL（Repository 抽象使切换低成本）；MinIO 可保留或换云 OSS |
